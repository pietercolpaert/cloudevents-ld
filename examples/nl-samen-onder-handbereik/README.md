# Samen Onder Handbereik: meeting outcome events (NL)

Three CloudEvents from the Dutch [Samen Onder Handbereik](https://samen-onder-handbereik.github.io/specificaties/) specifications, collaboration function *Uitwisselen Uitkomst Overleg* (exchanging the outcome of a case meeting):

| Event type | What it records |
|---|---|
| `nl.jzv.uitwisselen-uitkomst-overleg.uitkomst-beschikbaar-gesteld` | A meeting outcome was made available |
| `nl.jzv.uitwisselen-uitkomst-overleg.uitkomst-ingezien` | A meeting outcome was consulted |
| `nl.jzv.uitwisselen-uitkomst-overleg.uitkomst-overleg-query-resultaat` | The result of an information request |

The events are illustrative examples from the specification. The identifiers and personal data in them are fictitious.

## Files

* `events.json`: the three complete examples from the specification, as a CloudEvents JSON batch.
* `events.ttl`: generated by `npm run build:examples`, which applies [`../../context.jsonld`](../../context.jsonld) to `events.json`. It conforms to [`../../shapes.ttl`](../../shapes.ttl).
* `LICENSE.md`: the licence of the source.

## What this example shows

* **The payload is JSON-LD with its own context.** `datacontenttype` is `application/ld+json`, and every `data` value carries its own `@context` and `@graph`, built from PROV-O and an `soh:` vocabulary.
  * The envelope context keeps that payload as an `rdf:JSON` literal. If the envelope context also interpreted it, the payload's context would clash with our protected terms.
  * Because the payload is self-contained JSON-LD, it can be turned into RDF in a second step by parsing `ce:data` with any JSON-LD processor.
* **Payload graphs from different events overlap.** The meeting outcome `urn:uuid:…4e54` appears in the payloads of both the first and the second event. That is why payloads should be kept apart per event, for example as one RDF Message per event, instead of being merged into one graph.
* **The payload refers back to the envelope.** `soh:Activity.cloudEventId` in the payload repeats the CloudEvent `id`. A rule can use it to link the PROV activity in the payload to the event.
* **The examples omit `dataschema`.** The specification's tables require `dataschema` (`…/jsonschema/prov-jsonld.schema.json`) for these events, but the complete examples leave it out. We copied the examples as they are, without adding it.
