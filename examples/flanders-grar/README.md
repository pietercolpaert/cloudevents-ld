# Flanders address register (GRAR) change event

A real change event from the address change feed of the Flemish base registries (staging environment), taken from a first attempt at CloudEvents-LD in [Informatievlaanderen/OSLO-Data/cloudevents](https://github.com/Informatievlaanderen/OSLO-Data/tree/main/cloudevents). This version is adapted to the decisions in this repository.

## Files

* `events.json`: the events exactly as published, in the CloudEvents JSON batch format (`application/cloudevents-batch+json`). There is no `@context` in the events.
* `context.jsonld`: maps the producer-specific extension attributes, which CloudEvents does not define, to placeholder IRIs (prefix `basisregisters:`, namespace `https://example.org/basisregisters#`).
* `events.ttl`: generated by `npm run build:examples`, which applies [`../../context.jsonld`](../../context.jsonld) and `context.jsonld` to `events.json`. It conforms to [`../../shapes.ttl`](../../shapes.ttl).

## Converting

Apply the contexts externally. You can do this in one of two ways:
* Serve `events.json` with an HTTP `Link` header: `Link: <…/context.jsonld>; rel="http://www.w3.org/ns/json-ld#context"`. JSON-LD processors honour it for `application/json` and other `+json` media types, which includes the CloudEvents media types. A `Link` header can only point to one context, so the producer-specific terms would have to be served in a context that combines both.
* Pass the contexts as `expandContext`, for example with [jsonld.js](https://github.com/digitalbazaar/jsonld.js). This is what `npm run build:examples` does:

```js
const shared = JSON.parse(await fs.readFile('../../context.jsonld', 'utf8'))['@context'];
const local = JSON.parse(await fs.readFile('context.jsonld', 'utf8'))['@context'];
const events = JSON.parse(await fs.readFile('events.json', 'utf8'));
const nquads = await jsonld.toRDF(events, { expandContext: { '@context': [shared, local] }, format: 'application/n-quads' });
```

## Changes compared with the first attempt

The first attempt mapped the envelope onto existing vocabularies, mostly DCMI Terms, and the payload onto OSLO. Here the envelope maps onto the CloudEvents-LD vocabulary, and the payload stays an opaque `rdf:JSON` literal.

| JSON member | First attempt | Here | Why |
|---|---|---|---|
| (event IRI) | `@base` + `id` → `<…/changeevents/adres/1>` | blank node | `id` is only unique within `source`, so `id` alone cannot identify the event. |
| `specversion` | `ex:specversion` or `dct:conformsTo` | `ce:specversion "1.0"` | Keeps the attribute's literal value, as the CloudEvents spec defines it. |
| `time` | `dct:issued`, typed `xsd:date` | `ce:time`, typed `xsd:dateTimeStamp` | It is the time of the occurrence, not of publication. Also, `xsd:date` cannot hold a time of day, so that literal was invalid. |
| `type` | `dct:type as:Create` | `ce:type "basisregisters.address.create.v1"` | The event type is a producer-defined string. Mapping it to ActivityStreams is producer-specific and belongs in rules. |
| `source` | `dct:source` | `ce:source`, typed `xsd:anyURI` | `dct:source` means "derived from". `source` names the context of the occurrence. |
| `subject` | `dct:subject` | `ce:subject` | A string scoped by `source`, not a topic. |
| `datacontenttype` | `content:doctypeName` or `dct:format` | `ce:datacontenttype` | `content:doctypeName` is the name of an (X)HTML DOCTYPE. `dct:format` expects a resource, not a string. |
| `dataschema` | `basisregisters:dataschema` or `dct:conformsTo` | `ce:dataschema`, an IRI | The `basisregisters:` prefix was never defined, so it produced an IRI with a non-existent scheme. |
| `basisregisterseventtype` | `rdf:type` a changefeed class | `basisregisters:basisregisterseventtype` | This is a producer-specific extension attribute, holding a string. The example's own context maps it to a placeholder namespace until the base registries publish IRIs for their extensions. |
| `basisregisterscausationid` | `dct:identifier` | `basisregisters:basisregisterscausationid` | It identifies the cause of the event, not the event itself. `ce:id` is already the event's `dct:identifier`. |
| `data` | `rdf:value`, payload mapped to OSLO | `ce:data`, typed `rdf:JSON` | The payload is parsed separately; see the main [README](../../README.md). |

The GRAR-specific parts of the first attempt are still useful, but as a separate step after this envelope mapping:
* `basisregisters.address.create.v1` → `as:Create` (and `update`/`delete`);
* `basisregisterseventtype` → a changefeed class;
* the payload terms, such as `objectId` → `generiek:lokaleIdentificator`, `naamruimte` → `generiek:naamruimte` and `versieId` → `generiek:versieIdentificator`.

They belong in rules or in a payload mapping that reads `ce:data`, not in the envelope context.
